# ML Models Analysis and Circularity Limitations

## Executive Summary

The ML pipeline has been successfully implemented with WiSARD, MLP, and a majority-class baseline. Key findings:

- **MLP** achieved 74.36% test accuracy, significantly outperforming the baseline
- **WiSARD** collapsed to the majority-class behavior (62.44% accuracy), always predicting Edge
- **Majority classifier** achieved 62.44% accuracy (trivial baseline)
- The dataset is moderately imbalanced: 62.4% Edge, 37.6% Cloud

### Key Observations

#### 1. WiSARD Failure
WiSARD performed identically to the majority classifier, always predicting Edge. This indicates:
- The quantization (4 bits per feature) may be too coarse for the decision boundary
- The RAM address size (8) may be insufficient
- The random mapping may not capture the feature interactions effectively
- The tie-breaking rule (prefer Edge) combined with weak learning caused collapse to majority class

**Recommendation**: WiSARD needs hyperparameter tuning (bits_per_feature, ram_address_size) to be competitive.

#### 2. MLP Performance
MLP achieved meaningful improvement over the baseline:
- 19% relative improvement in accuracy (62.44% → 74.36%)
- Successfully learned to predict both classes (1482 Edge, 768 Cloud)
- Better F1 scores for both classes, indicating balanced learning
- However, still has significant error rate (25.6%)

#### 3. Class Imbalance Impact
The dataset imbalance (62.4% Edge vs 37.6% Cloud) affects evaluation:
- Majority classifier achieves 62.44% accuracy by always predicting Edge
- F1 Cloud is more informative than accuracy for imbalanced datasets
- MLP's F1 Cloud (0.64) shows it learned the minority class reasonably well

## Circularity Limitations

### The Fundamental Issue

**CRITICAL**: The labels in this dataset were generated by the C# analytical simulator (`label_source = "analytical_simulator"`). This creates a methodological circularity:

```
C# analytical formula → labels → ML training → ML model
                                            ↓
                                    reproduces formula
```

### Implications

1. **Not Generalization**: High accuracy does **not** indicate the model will generalize to real-world scenarios. It only indicates the model learned to reproduce the analytical formula.

2. **Formula Dependency**: The model's "intelligence" is limited to the assumptions encoded in the C# analytical simulator (latency model, resource assumptions, network conditions).

3. **Overestimation of Performance**: The 74.36% accuracy may be overstating real-world capability since the test distribution comes from the same synthetic process.

4. **Decision Boundary Analysis**: If the analytical formula has simple decision boundaries (e.g., "if CPU > X then Edge"), ML models may achieve high accuracy by learning these simple rules rather than complex patterns.

### Label Investigation

The confusion matrices reveal important information:

**MLP Confusion Matrix (Test)**:
|                | Predicted Edge | Predicted Cloud |
|----------------|---------------:|---------------:|
| Actual Edge    | 1155           | 250            |
| Actual Cloud   | 327            | 518            |

**Analysis**:
- 82.2% of Edge samples correctly classified (1155/1405)
- 61.3% of Cloud samples correctly classified (518/845)
- 250 Edge samples misclassified as Cloud (17.8%)
- 327 Cloud samples misclassified as Edge (38.7%)

The asymmetric error rates suggest:
- The decision boundary is not trivial (otherwise accuracy would be higher)
- There is overlap between Edge and Cloud regions in feature space
- The analytical formula may produce ambiguous cases near the boundary

### Comparison with Baselines

The MLP's performance should be interpreted relative to the baselines:

- **vs Majority**: +19% relative accuracy improvement is meaningful
- **vs Random**: Expected random accuracy = 50%, MLP is 24.6% absolute points higher
- **vs Perfect**: 25.6% error rate indicates significant room for improvement

### Recommendations for Next Steps

1. **Investigate Analytical Formula**: Examine the C# `EdgeCloudSimulator.cs` to understand the decision logic. If the formula is simple (e.g., linear threshold), high accuracy is expected and not impressive.

2. **Feature Importance Analysis**: Determine which features drive the predictions. If one feature dominates, the "ML" aspect is minimal.

3. **Edge Case Analysis**: Examine the misclassified samples to understand if they represent:
   - Ambiguous cases near the decision boundary
   - Noisy labels from the analytical simulator
   - Genuine complexity in the offloading decision

4. **Hyperparameter Tuning for WiSARD**: The current WiSARD configuration failed completely. Consider:
   - Increasing `bits_per_feature` (currently 4)
   - Adjusting `ram_address_size` (currently 8)
   - Different random seeds
   - Alternative tie-breaking strategies

5. **Independent Validation**: Before claiming ML effectiveness, validate against:
   - Real-world traces (if available)
   - EdgeSimPy simulation with different scenarios
   - The C# simulator with different parameters

## Conclusion

The ML pipeline is functional and produces reproducible results. However, the circularity limitation means:

1. **Do not claim** that MLP is "intelligent" or "learned complex patterns" based on accuracy alone
2. **Do claim** that MLP outperforms trivial baselines on reproducing the analytical formula
3. **Investigate** the analytical formula to understand what MLP actually learned
4. **Validate** against independent scenarios before drawing conclusions about real-world performance

The next step should be integrating these models into EdgeSimPy to evaluate system-level metrics (latency, deadline violations, throughput) rather than just classification accuracy.
